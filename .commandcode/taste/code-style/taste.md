# code-style
- Use "X" instead of "Twitter" in user-facing labels, but keep "twitter" in variable/property keys. Confidence: 0.65
- Maintains PHP 7.4 compatibility (readme.txt `Requires PHP: 7.4`; phpcs `testVersion="7.4-"`). Arrow functions (`fn`) are allowed and are the preferred concise form for simple single-expression callbacks (e.g., an `array_filter` predicate) — replaced a closure with `fn( $meta_key ) => ...` once 7.4 was enabled. phpcs must still pass on changed files. Confidence: 0.9
- Flags and removes dead/redundant defensive checks — e.g., an `is_protected_meta()` guard on a key that can never be protected (so the expression is always true) should be deleted, not kept as token defense-in-depth. Confidence: 0.85
- Prefers compact, single-line implementations for simple functions — explicitly asked to collapse a multi-line if/else return into a one-line ternary (`? :`). Confidence: 0.9
- Wants minimal comments: considers verbose docblocks and explanatory comments on simple/obvious code redundant ("thừa thãi"); keep only necessary inline annotations such as `phpcs:ignore`. Comments should be short — explicitly asked to condense a two-line explanatory comment down to a single line. Confidence: 0.9
- Values simple, readable code over abstraction for trivial logic: when the "shared" logic across classes is only a single self-describing WP core call (e.g. `current_user_can( 'edit_post', $post_id )`), prefers keeping the inline call at each site rather than extracting a helper class — tried `Helpers\Permission` for it, then reverted on reflection because the wrapper (file + import + namespace) added indirection without reducing complexity, and two same-named `can_edit_post` methods (one with a Contributor fallback, one without) were more confusing than before. Inline `current_user_can()` matches the codebase's existing style; a dedicated class is only justified by genuinely non-trivial shared logic or by grouping multiple future checks (e.g. `can_edit_term`, `can_manage_options`). Confidence: 0.9
- When a bug is caused by ambiguous short class names across namespaces (e.g. both `SlimSEO\Helpers\Data` and `SlimSEO\MetaTags\Data` exist and a file needs both), accepts alias-based fixes following the repo's existing patterns (`DataHelpers`, `HelpersData`) as sufficient — prefers not to restructure code (e.g. extracting a new class) just to remove aliasing, since that adds indirection for trivial logic. Confidence: 0.7
- Leans toward PHP string interpolation (e.g. `"/$current_path/"`, `"%$taxonomy%"`) over string concatenation (`'/' . $current_path . '/'`, `'%' . $taxonomy . '%'`) when it reads more clearly — proposed the interpolation form as an alternative and the user explicitly confirmed the switch ("đổi"), then asked to convert the remaining concatenation spots in the same file too ("đổi cả chỗ % nữa"), so the preference is general: sweep all concatenations that read better as interpolation, not just the originally-discussed pattern. Confidence: 0.85
- Cares about clear, concise naming for public filters/hooks: flagged `slim_seo_primary_term_supported_rewrite_post_types` as too long ("dài") and unclear ("chưa rõ nghĩa"), and asked for alternative names. Expects hook names to be short, self-descriptive, and consistent with the codebase's `slim_seo_` + context + object + parameter convention, avoiding redundant word repetition (e.g. "supported rewrite post types"). When offered alternatives, ultimately settled on the shortest one — `slim_seo_primary_term_rewrite` over the more descriptive `..._rewrite_post_types` (and rejected `rewrite_rules` for colliding with WP's rewrite-rules terminology) — preferring brevity in public hook names over extra descriptiveness; treats pre-release rename as cheap, so keeps weighing options before finalizing. Confidence: 0.9
