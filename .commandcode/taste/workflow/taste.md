# Taste — Workflow

- Uses the branch-name prefix `cursor/` with short descriptive names (e.g., `cursor/fix-preview-post-meta-disclosure`). Confidence: 0.8
- When renaming a public filter/hook, expects the rename to be done end-to-end: the related method renamed for consistency, a CHANGELOG note added (public filters may be used by other themes/plugins, so the rename is a breaking change that must be documented), and a grep sweep for any remaining references to the old name. Confidence: 0.65
- When asked to "create a branch, commit and create a pr", expects the whole contribution workflow completed end-to-end: a descriptive branch, a single commit covering the changes, a push to origin, and a PR opened via the gh CLI (`gh pr create`), with temporary helper files cleaned up afterwards. Confidence: 0.7
- Keeps version/requirement declarations consistent across all files — readme.txt, phpcs.xml (`testVersion`), composer.json, AGENTS.md. readme.txt is treated as the source of truth for the minimum PHP version; when it changes, updates every other declaration together (and hunts down stragglers via grep). Confidence: 0.8
- When phpcs flags an idiom that is actually correct WordPress practice (e.g., the dynamic meta capability `edit_term`, which the sniff doesn't recognize), prefers suppressing the specific sniff with an inline `// phpcs:ignore <sniff> -- <reason>` comment over rewriting the code or changing global config — matching the codebase's existing `phpcs:ignore` pattern for direct DB queries. But first verifies against official core sources that the idiom is truly correct before suppressing. Confidence: 0.75
- When committing: stages only the changes worked on, excludes unrelated files, and writes a concise commit message; pushes to remote only when explicitly requested — the user says "commit & push" explicitly when a push is wanted, and repeats the exact terse phrase to request a full commit+push round-trip. Confidence: 0.8
- When a follow-up change concerns the same fix already committed and pushed to an open PR, prefers creating a new commit and pushing it over amending the existing commit and force-pushing — explicitly chose "tạo commit mới và push" when offered the amend+force-push option; repeatedly applies this on subsequent review rounds without amending or force-pushing. Confidence: 0.85
- Wants PR-related writing — both PR descriptions and PR review feedback — in Simple English and kept concise ("ngắn gọn", `/simple-english`): short sentences (~20–25 words max), one idea per sentence, keep function names and file paths verbatim, avoid "should" and semicolons. Confidence: 0.9
- When reviewing a PR, reports only the points that need fixing — explicitly asked "chỉ ghi những điểm cần phải sửa" — with no praise or commentary about what is fine; issues are listed concisely (per /simple-english, in Vietnamese) as actionable fixes, most serious first. Confidence: 0.8
- When an AJAX endpoint is changed to return error statuses (e.g. 403), verifies the JS consumer tolerates it — the codebase's `fetch()` calls have no `.catch`, only `.then().then()`, so a 403 must resolve cleanly (it does: `fetch` only rejects on network errors; the handler's `if ( ! success ) return;` skips populating the UI). Confidence: 0.6
- Wants commit messages written in ASD-STE100 Simplified Technical English via the manually-attached `ste-writing` skill: active voice, short sentences (~20 words instruction / 25 descriptive), no contractions, no semicolons, no em dashes, American spelling, imperative form. Confidence: 0.85
- Expects PR review deliverables to be saved to a markdown file in the repo (e.g., `review.md` in the repo root), not just delivered in chat — explicitly asked "xuất review ra file review.md". Confidence: 0.55
- When given a bug report and a candidate PR, expects the review to verify whether the fix fully resolves the reported bug's actual root cause (not just whether the diff is code-correct): trace the real cause across related source files first, then judge whether any gaps/edge cases remain and whether a better, more general fix exists (e.g., a `user_trailingslashit()` normalization at the URL source vs. handling one specific page type) — asked "pr này có fix được lỗi này trọn vẹn ko, còn vấn đề gì còn sót, hoặc có cách fix tốt hơn ko". Confidence: 0.7
- Rejects blanket trailing-slash normalization (e.g. forcing `trailingslashit()`/`user_trailingslashit()` across URL outputs) as a general URL fix, because it breaks setups where permalinks have NO trailing slash. Prefers instead deriving the URL from the actual page permalink (e.g. `get_permalink($archive_page)`) so it always matches the page's real URL regardless of permalink configuration — explicitly dismissed the `trailingslashit()` approach as "mạo hiểm". Confidence: 0.9
- When tracing URL/trailing-slash bugs, wants the differing behavior between contexts explained concretely (e.g. why the shop URL has a trailing slash inside single-product breadcrumbs but not on the shop page canonical) — by checking core behaviors like `get_post_type_archive_link()` calling `user_trailingslashit()` and how `has_archive` string vs boolean affects `get_post_type_archive_link`/`get_page_by_path`. Confidence: 0.7
- When fixing a bug/error, expects a sweep for the same class of problem across the whole codebase, not just the reported file — e.g., after a duplicate-class-name bug in one file, "kiểm tra tất cả các chỗ khác tương tự" (check all other similar places) for the same colliding import. Confidence: 0.6
- Is open to revising and reverting an approach after trying it: when reflection shows an extraction added complexity without real benefit (e.g. a `Permission` helper class wrapping one WP core call), expects a clean revert to the original files (`git checkout` on all touched files, delete new file) rather than keeping the refactor. Confidence: 0.85
- Maintains CHANGELOG.md as a release log: when asked "viết những thay đổi từ version mới nhất đến hiện tại vào file CHANGELOG.md", expects a new entry prepended at the top as a dated `### x.y.z - YYYY-MM-DD` header summarizing all commits since the latest git tag, grouped by type (new features, fixes, removals/updates), each bullet referencing its issue/PR number (#271), with the version number derived from repo conventions (minor bump when a new feature is included). Confidence: 0.6
- In the plugin's marketing docs (README.md / readme.txt), a discrete feature belongs inside the unified "Features" section as a numbered item — not as a standalone top-level section. When the AI section was given its own heading, explicitly asked to fold it into Features ("phần AI-Powered Meta Tags là 1 tính năng, nên đưa nó vào phần Features") and expects the remaining features renumbered to stay sequential and consistent across both files. Confidence: 0.7
- Treats the plugin's public title/tagline as a search/SEO asset, not just a label: wants popular search keywords (e.g., "AI SEO") worked into the title while still emphasizing the product's core differentiators (fast, automated, lightweight/no bloat) — asked "thêm từ khóa AI SEO vào, nhưng vẫn nhấn mạnh được điểm khác biệt" and expects options that balance keyword reach against brand identity rather than replacing the differentiators outright. Confidence: 0.55
- When the plugin's public title/messaging changes, expects the marketing/documentation files (README.md and readme.txt) to be rewritten in the same effort to match the new title — including adding a description of newly highlighted features (e.g., an AI section) that accurately reflects what the plugin actually implements — and expects the title/description to stay consistent across README.md, readme.txt and the plugin header. Confidence: 0.6
