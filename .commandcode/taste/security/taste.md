# Taste — Security

- Prefers fast-path ordering in capability checks: check the general capability (e.g. `current_user_can( 'edit_post', $post_id )`) first and return early, then handle the special-case fallback only when the general check fails — avoids redundant work (e.g. an unnecessary `get_post()`) and keeps the common path simple. Confidence: 0.8
- Scopes permission fallbacks to the exact post status that motivates them: a fallback for roles lacking `edit_published_posts` (Contributor previewing their own published post) is locked with a `post_status === 'publish'` check, since the author's own drafts/private posts are already covered by `edit_post`. Confidence: 0.8
- Prefers minimal, permission-based fixes over blanket restrictions: when fixing an access-control bug, check the proper capability (e.g., `current_user_can( 'edit_post', $id )` before reading meta) rather than stripping/filtering all protected data, so legitimate users with the right permissions are not blocked (questioned whether an `is_protected_meta` filter would break authorized access; also flags when a fix regresses a legitimate use case, e.g. Contributors previewing their own published posts). Confidence: 0.85
- When a permission fix regresses a legitimate use case, restore it with a narrowly-scoped fallback grounded in verifiable data — e.g., allow a Contributor to preview their own published post only when the DB-stored `post_author` equals the current user, never on a claimed/guessed author — since `post_author` cannot be spoofed via the request and preview routes return full `post_content`, so any broader fallback would leak other authors' posts. Applies the fallback to preview only, not to other handlers like quick-edit. Confidence: 0.85
- Values defense-in-depth but scoped: filtering protected meta keys out of endpoints that expose only key names (no values) is welcome, while capability checks stay on endpoints that return values. Confidence: 0.65
- Expects a security fix to cover the same class of gap in sibling handlers (e.g., the term variant of a post AJAX endpoint), not just the reported path. Confidence: 0.6
- Credits security researchers/reporters in the changelog entry for each security fix (e.g., "Credit Shivamani Vastrala"). Confidence: 0.7
- Scrutinizes capability checks for correctness across all taxonomies/object types, not just the common case: a hardcoded cap like `manage_categories` is wrong for tags and custom taxonomies (e.g., WooCommerce `product_cat`). Term-editing checks should use the core meta cap `current_user_can( 'edit_term', $term_id )` (introduced in WP 4.7) — which `map_meta_cap()` resolves to the taxonomy's registered cap (default `manage_categories`, custom caps like `edit_products`), and fails safe (false) for nonexistent terms — rather than the raw plural cap `edit_terms` or a hardcoded taxonomy cap. Confidence: 0.85
- Guards permission fallbacks against unauthenticated requests: any ownership comparison must require a logged-in user (`get_current_user_id() > 0`), because a logged-out visitor's user ID is 0 and posts with `post_author = 0` (common in imported/script-created content) would otherwise match `0 === 0` and let anonymous visitors through the route's only gate. Matches WP core's own behavior of never taking the owner branch when `post_author` is 0. Confidence: 0.8
- Does not rely on ownership alone in a permission fallback for a route that reads full post meta: in addition to a logged-in user, requires the base editing capability (`current_user_can( 'edit_posts' )`), because subscriber-level accounts can be recorded as a published post's `post_author` through front-end submission, directory or forum plugins, and would otherwise pass an ownership-only gate. Keeps the intended Contributor preview (Contributors have `edit_posts`) while excluding subscriber authors. Confidence: 0.8
 When consolidating repeated capability checks into a shared helper, keeps the helper strict — only the common check (pure `current_user_can( 'edit_post', $post_id )`) — and leaves special-case fallbacks (Contributor previewing own published post) in the single place that needs them, so extracting the helper doesn't widen permissions elsewhere (Contributors must not gain the ability to set primary term or generate AI). Confidence: 0.8
- Questions whether extra capability checks (e.g. `read_post` alongside `edit_post` in `PrimaryTerm`) are necessary, and prefers dropping ones that add no real barrier — verified against WP core's `map_meta_cap()` semantics: on published posts `read_post` maps to the trivial `read` cap (every role has it), on others' draft/private posts it maps back to `edit_post` (already checked), and private posts need `read_private_posts`, which accompanies `edit_private_posts` in the same role caps; WP's default meta cap for `register_post_meta` is `edit_post` and the rest of the plugin only checks `edit_post`, so the extra check is both redundant and inconsistent. Confidence: 0.7
